# Crane 项目能力说明文档设计

## 目标

新增 `docs/project-capabilities.zh.md`，面向技术与产品选型评估者，基于当前分支的实际实现说明 Crane 能解决什么问题、需要部署哪些组件、能力是否默认可用，以及仍存在哪些交付边界。

新文档不重复 `docs/project-implementation-architecture.zh.md` 的研发架构和扩展点分析。涉及实现细节时提供关键代码证据，并引导读者查阅现有架构文档。

## 读者与使用场景

主要读者包括技术决策者、平台产品经理、云原生平台架构师和负责方案选型的研发人员。文档应帮助读者完成以下判断：

- Crane 是否覆盖目标 FinOps 与 Kubernetes 资源优化场景。
- 各项能力需要哪些 Crane 组件、外部项目、监控系统或云厂商接口。
- 哪些能力默认启用，哪些需要 Feature Gate、独立部署或二次建设。
- 当前实现是否已经形成用户可使用的闭环。
- 引入项目时需要接受哪些版本、成熟度、安全和运维风险。

## 分析范围

分析当前仓库中的源码、配置、部署清单、CRD、测试和用户文档，重点覆盖：

- `craned`、`crane-agent`、`metric-adapter`、`cost-collector` 四个后端进程。
- Dashboard 与 `craned` Web API。
- 成本采集、资源推荐、弹性伸缩、时间序列预测、QoS 保障、节点资源和平台支撑能力。
- 阿里云、华为云、腾讯云、火山引擎账单 Provider。
- Fadvisor、crane-scheduler、Prometheus、metrics-server 等外部依赖。

外部仓库的能力只作为依赖或组合方案说明，不计为本仓库已经实现的能力。

## 取证原则

源码、Feature Gate、CRD、部署清单和测试属于一级证据；README、教程和提案只用于补充产品背景。文档描述与当前代码冲突时，以当前分支代码为准，并在限制或风险中指出差异。

分析时系统枚举以下对象：

- 可执行进程及其启动配置。
- controller、recommender、predictor、provider 和 executor 注册项。
- CRD、Feature Gate、Web API、Prometheus 指标与部署资源。
- 推荐结果采纳、预测指标消费、成本账单持久化等关键闭环。
- 与能力直接相关的测试和配置示例。

每项重要结论至少关联一个关键文件。判断一项能力是否形成闭环时，同时核对入口、配置、处理链路、输出或消费端，避免仅凭目录名和文档宣称下结论。

## 状态模型

每项能力使用一致的字段进行说明：

- 解决的问题与适用场景。
- 当前实现和用户可获得的结果。
- 必需组件、数据源与基础设施。
- 启用方式：默认启用、Feature Gate、独立部署或外部依赖。
- 交付状态：已形成闭环、部分闭环、底层能力或外部能力。
- 主要限制与不适用场景。
- 对应代码、配置或清单证据。

成熟度判定只依据当前实现。所有在 `pkg/features/features.go` 中标为 Alpha 的 Feature Gate 必须如实标注；独立进程不能因为代码存在就视为已集成进 Dashboard；外部项目不能计入仓库内交付范围。

## 文档结构

最终能力说明采用能力域评估型结构：

1. 执行摘要：项目定位、适合与不适合的场景、整体完成度。
2. 能力状态图例：解释启用方式、交付状态和外部依赖标记。
3. 能力全景矩阵：汇总能力域、核心能力、交付状态、关键依赖和主要限制。
4. 多云成本与 FinOps：账单采集、云厂商 Provider、费率目录、分摊、对账、账本和指标暴露。
5. 资源分析与优化推荐：资源、HPA、副本、闲置节点、Service、Volume 推荐，以及规则调度和结果采纳。
6. 弹性伸缩与预测：EHPA、EVPA、周期与预测弹性、TimeSeriesPrediction、指标适配器和数据源。
7. QoS、节点资源与调度：异常检测、禁调度、限流、驱逐、CPU 管理、资源拓扑，以及外部调度器边界。
8. 平台与运维支撑：Dashboard、Web API、监控指标、Webhook、Feature Gate、部署方式和多集群边界。
9. 典型部署组合：基础推荐、预测弹性、节点 QoS、多云成本采集等组合的组件清单。
10. 选型结论与风险清单：适用条件、关键缺口、兼容性、安全、状态持久化和运维风险。
11. 代码证据索引：按能力映射关键入口，并链接现有研发架构文档。

## 已知重点结论

后续取证必须验证并准确表述以下已经从仓库初查中发现的边界：

- 当前仓库新增了独立 `cost-collector`，支持四家云厂商账单，但其账本和指标不应直接等同于完整成本可视化产品闭环。
- Fadvisor 和负载感知 crane-scheduler 属于外部项目。
- Crane 的 Feature Gate 当前均标记为 Alpha，其中部分默认开启、部分默认关闭。
- 推荐框架包含多种 recommender，但不同推荐类型的结果完整度、采纳方式和用户入口需要分别核实。
- QoS 和 CPU 管理涉及节点级特权、CRI、cgroup 与内核环境，部署前提必须明确。
- Dashboard 和 Web API 的存在不代表所有底层能力都有对应的可视化与控制入口。

## 验收与校验

最终文档完成后执行以下检查：

- Markdown 标题层级、表格和相对链接有效。
- 状态术语在全篇含义一致。
- 不包含 `TODO`、`TBD`、占位内容或无证据宣传语。
- 执行摘要、能力矩阵、各能力域和风险清单之间没有矛盾。
- 每项主要能力都说明依赖、启用方式、交付状态和边界。
- 当前仓库能力与外部项目能力有明确区分。
- 文档不展开已有架构文档已经覆盖的代码级实现细节。

验收结果应使选型评估者无需阅读源码，即可判断 Crane 能做什么、需要部署什么、哪些能力默认可用，以及哪些能力仍需外部组件或二次建设。
